## 2. 背景与定位

现在「整站深度代理」是在**我们的网关**上做：访客所有流量（页面、图片、脚本、审核站整站）都经过网关回源与改写。问题是**所有带宽都压在我们服务器**，客户站点一大就扛不住，成本也高。

新定位：**深度代理放到客户自己的服务器里执行**。客户在其服务端代码里集成我们的 SDK，用我们给的密钥和网关地址配置好。网站入口处：

1. SDK 调用我们的**判定接口**（一个很小的 JSON 请求）拿「放行 / 审核」结论。
2. **放行**：客户服务器照常输出自己的真实网站。
3. **审核**：由**客户服务器**去抓审核站内容，把审核站域名改写成客户域名后输出；地址栏保持客户域名、站内链接不跳走。

这样：

- 我们的网关只承载判定 JSON（每次访问 < 1KB 级），**带宽压力极小**。
- 审核站整站的回源与改写流量走**客户服务器**，谁的量谁承担。
- 客户用主流语言的 SDK，几行代码接入，不用改架构、不用把 DNS 指到我们。

> 原来的「网关托管深度代理」作为**备选**保留：适合纯静态站、无法在服务端跑代码、或客户主动要零代码接入的场景。能在服务端跑代码的，一律优先用 SDK。

## 3. 名词

| 词 | 含义 |
| --- | --- |
| 判定接口 | 我们提供的 `/api/open/v2/decision`，输入访客上下文，输出放行/审核等结论 |
| 真实内容 | 客户自己的网站 |
| 审核站 | 送审时展示的站点（如 `review.com`），由客户服务器代理改写 |
| 深度代理（SDK 内） | 在客户服务器抓审核站、改写域名、输出，使地址栏不变、站内链接不跳走 |
| 服务端密钥 `sk_` | 客户服务器调用判定接口用的密钥，只放服务器 |

## 4. 目标用户与语言

能在服务端出代码的客户。首期官方 SDK 覆盖主流后端：

| 语言 | 形态 |
| --- | --- |
| PHP | Composer 包 + 现成 WordPress 插件（已存在，升级为含深度代理） |
| Node.js | npm 包（Express / Koa / 原生 http 中间件） |
| Go | Go module（`net/http` 中间件 / handler 包装） |
| Java | Maven 包（Servlet Filter / Spring 拦截器） |
| Python | pip 包（WSGI / ASGI 中间件，兼容 Django / Flask / FastAPI） |

各语言 SDK 对外能力一致（见 §6），只是按各自生态封装。

## 5. 接入流程（客户视角）

1. 后台站点管理：接入方式选「服务端接入」。创建服务端密钥 `sk_`。
2. 配置审核站地址（如 `https://review.com`）与真实站（就是客户自己）。
3. 在客户服务器安装对应语言 SDK，填入：网关地址、`sk_`、审核站地址、客户自己的对外域名。
4. 在网站入口（框架中间件 / 入口文件）挂上 SDK：
   - 跳过后台、登录、支付回调、静态资源等路径。
   - 调判定接口拿结论。
   - 放行 → 继续自己的业务；审核 → 调用 SDK 的「深度代理审核站」方法输出。
5. 验收：无参数访问看审核站（地址是客户域名）；带归因码看真实站；同浏览器回访仍真实。

## 6. SDK 能力要求

每语言 SDK 必须提供：

### 6.1 配置

- `apiBase`（网关地址）、`secretKey`（`sk_`）、`reviewOrigin`（审核站地址）、`visitorHost`（客户对外域名，可从请求 Host 自动取）。
- 可选：超时（默认 3s）、失败策略（默认按审核处理）、判定缓存 TTL、跳过路径规则、真实访客 IP 头（如 `CF-Connecting-IP`）。

### 6.2 判定

- 采集当前请求：完整 URL、方法、访客令牌 Cookie、IP、UA、Referer、Accept-Language。
- 用 v2 签名（HMAC-SHA256，带时间戳 + nonce）调 `/api/open/v2/decision`。
- 解析返回：`content`（real/review/bypass/block/not_found）、`cookie`（放行时种访客 Cookie）、`handoffUrl` / `handoffBanner`（内置浏览器引导）。
- 失败（超时 / 非 200）：按「审核」处理，绝不泄露真实内容。

### 6.3 深度代理审核站（本次新增核心）

判定为审核时，SDK 在**客户服务器**内：

1. 向 `reviewOrigin` 发起回源请求（转发访客的 path+query、方法、必要请求头；带 `Accept-Encoding: identity` 以便改写）。
2. 把响应正文里的**审核站域名改写成客户域名**，覆盖：
   - HTML 的链接、图片、脚本、样式、表单 `action`；
   - 页面内及单独返回的 JS / JSON / XML 里写死的审核站域名，含 `https:\/\/review.com` 转义写法与 `%3A%2F%2F` 百分号编码写法；
   - CSS 的 `url(...)`；
   - 响应头 `Location`（301/302）与 `Set-Cookie` 的域名。
3. 其它域名、第三方 CDN 保持原样。
4. 把改写后的正文与安全响应头输出给访客：状态码透传、`Cache-Control: no-store`、审核加 `X-Robots-Tag: noindex`，可由 SDK 自行按 `Accept-Encoding` 压缩。
5. 可选：改写后的审核页在客户服务器侧**缓存**（按 站点+路径），减少回源。

> 改写规则必须与我们网关一致，保证同样的覆盖面与边界（见技术方案）。

### 6.4 放行

- 放行 / bypass：不代理，交回客户自己的业务继续渲染，并按返回种访客 Cookie。

### 6.5 其它

- 转化上报：`/api/open/v2/conversions`（可选）。
- 内置浏览器引导：返回 `handoffUrl` 时，SDK 可注入「在浏览器打开」提示条（和现有逻辑一致）。
- 跳过规则：后台、登录、REST、Cron、静态资源默认跳过。

## 7. 与现有能力的关系

- 判定接口、签名、配额、全局开关、日志全部复用现状，不改协议。
- 审核内容若选「平台模板」，SDK 直接用返回的 `renderHint.html`，无需回源审核站（最省）。选「审核源站」则走 §6.3 深度代理。
- WordPress 插件从「只判定 + 平台模板 / 外链」升级为「可在插件内做审核站深度代理」，与多语言 SDK 对齐。

## 8. 验收

1. 客户服务器集成 SDK 后，无参数访问展示审核站内容，**地址栏是客户域名**，点站内链接仍停在客户域名、不跳到审核站。
2. 带有效归因码访问展示真实站；同浏览器再访问无参数仍真实。
3. 审核站页面里的链接、图片、脚本、样式、表单、JSON/JS 中的审核域名、`Location`、`Set-Cookie` 均被改写成客户域名；第三方域名不变。
4. 判定接口超时或出错时展示审核站或审核兜底，不泄露真实内容。
5. 访客的页面与静态资源流量**不经过我们的网关**；我们这边只看到判定调用。
6. 五种语言各有可运行的最小示例，照做即可通过第 1–4 条。

## 9. 不在本阶段

- 把现有网关托管深度代理下线（继续作为备选）。
- SDK 内的可视化配置界面（配置用代码 / 配置文件）。
- 审核站需要登录态、复杂反爬的站点适配。
- gRPC / 其它非 HTTP 框架适配。
